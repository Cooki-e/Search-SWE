# Available Resources

The task runtime has no public network access. Use only the supplied vectors,
task data, installed Python packages, and system tools. Do not download models,
datasets, labels, result mappings, packages, or remote retrieval results.

The coding agent's own model connection is a Harbor phase-scoped exception and
does not grant the submitted search system access to that model or to the
internet. The final system must run entirely from local task inputs.

Both phase containers provide 16 CPUs for development and offline construction, 512 MiB aggregate memory, no swap, 100 GiB storage allowance and no GPU. Final online queries have a separate one-logical-CPU budget: the client, restarted service and every descendant share the same single allowed CPU. Both phases use a per-process open-file soft and hard limit of 1,048,576, including non-root verifier build and query processes. The memory cgroup includes the build, resident service, clients, all descendants, charged file-cache pages, and runtime/verifier overhead; it is not a per-process allowance. Both agent development and final verification have a 120-minute total limit. Failed development experiments do not by themselves set the final reward; final verification starts in a fresh container. The final build has a 150-second limit and each query has a 0.5-second hard deadline. The 100 GiB storage allowance is an audited policy, not a kernel filesystem quota; index sizes are reported.

For representative query tests, first terminate only your own build-started search service, then run `/usr/local/bin/search-swe-query-cpu /app/run.sh` with the normal query arguments. The identical protected launcher is provided in both images and used automatically by the verifier for every query. It selects the first CPU in the permitted affinity mask, pins execution there and prevents later affinity expansion across threads, forks and execs. It configures OpenMP with `KMP_AFFINITY=disabled` and `OMP_PROC_BIND=false`, and clears `GOMP_CPU_AFFINITY`, so numerical runtimes keep the inherited mask. Do not re-enable runtime affinity changes. Submitted query executables must use the image's native 64-bit architecture. Build-time services are terminated before this boundary; a development service left running with the build's wider CPU access would give an unrepresentative measurement. Launcher startup is included in the existing query deadline and latency measurement. The CPU is not reserved exclusively, and the verifier does not change the host scheduler or flush caches.

The supplied index workspace is `/task/index`, a fresh 64 MiB (67,108,864-byte) tmpfs mounted in both phases. Use it as `--index-dir` for representative development tests and final execution. All final build and query artifacts, including indexes, document lookup tables, executables, logs, temporary files and caches, must fit there throughout the final build and query workload; the kernel rejects writes beyond its capacity. The requested result JSONL file is the exception and must be written to the supplied `--output` path. Sparse files also count by logical size for the grader limit. This workspace is charged to the same 512 MiB memory cgroup, not an additional memory allowance. Keep submitted source files and development scratch files under `/app` within the general storage allowance. The timed final build must derive corpus-dependent search state from the supplied inputs; it must not reuse prebuilt corpus indexes or learned search tables bundled with the source. Do not place generated search state elsewhere or use other persistent writable paths or query-output directories to evade the workspace budget. Anonymous memory and IPC shared memory are permitted within the total memory budget, but shared-memory files are cleared during the post-build restart and cannot preserve an index across it. The supplied corpus remains read-only and may be read for genuine retrieval and reranking.

The verifier starts from an empty index workspace and builds once. After the successful build, it terminates all submission processes while preserving the workspace and clearing IPC shared memory, to verify that the stored index can be deployed independently. The first run.sh call must automatically load that stored state and start its service if needed; this cold startup is included in that call's 0.5-second deadline and latency. Later calls may reuse the service for one sequential pass over 20 distinct hidden queries in fixed stored order. There is no hidden-query warmup or repeated hidden-query round. The verifier does not flush the operating-system file cache; file pages and index state created during the build may remain cached. P95 is the nearest-rank quantile: sort all 20 end-to-end durations and take the 19th (one-based, `ceil(0.95 * 20)`). Timeouts and failed launches contribute 0.5 seconds; all other invocations, including nonzero exits and invalid outputs, contribute their externally measured duration capped at 0.5 seconds. Timing uses a monotonic clock and Linux process-exit events, from immediately before process creation through observed exit; query input reading, communication, retrieval, result output and exit are included. Timeout termination and cleanup are recorded separately and do not inflate completed-query latency. A timed-out client is terminated while a separately started query service remains available for subsequent queries. Nonpositive or nonfinite timings invalidate evaluation. Independent author reruns start a fresh build and service; they measure stability and do not increase the count of distinct queries.

Let `A` be the mean of the 20 latency-gated Accuracy@3 values and `L95` the P95 duration in seconds. The service must achieve `A >= 0.95`: at least 19 of the 20 queries must pass the accuracy, output and 0.5-second execution gates. Below this quality floor the reward is zero. At or above it, the normalized reward before the integrity gate is `A * min(1, 0.030 / L95)`; the displayed score is 100 times this reward. Accuracy and the latency factor are still reported when the quality floor is missed. This is an acceptance threshold on this fixed workload, not a statistical confidence guarantee. At `A=1`, P95 values of 30, 60 and 150 ms earn 100, 50 and 20 points. At `A=0.95`, 30 and 150 ms earn 95 and 19 points; `A=0.90` earns zero regardless of speed. A failed build, invalid or oversized index, invalid evaluator inputs, out-of-memory kill observed in the final verifier container, or failed retrieval-integrity check makes the overall reward zero.
